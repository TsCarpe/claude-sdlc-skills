# issues 文件模板（严格模板：结构不得增删，区块无内容写「无」）

路径：`sdlc/<需求名>/review/issues-<日期>.md`（新一轮 `-r<N>`）。

产物以**宽表**为基本单元：一行一条 issue；「问题标题」「场景（白话）」「原文摘引」三列保证裁决者不打开设计/用例原文也能理解问题本体与业务场景。头部「业务背景」行与「代号速查」小节保证冷启动读者（线下看文件/下一轮/事后审计）不翻 design/digest 也能锚定。单元格内多段内容用 `<br>` 分行（对齐 sdlc-test 用例可读性硬规则），禁止把多个语义段挤成一行。

## 目录

> 本目录是 issue-template.md 自身的导航（本文 >100 行，供部分读取时预览范围），非产物内容；产出的 issues 文件按下方 fenced 模板主体结构产出，不含此目录。

- 模板主体：头部 kv（含业务背景）／代号速查 ／ 〇 速览与裁决焦点 ／ 一 分歧清单 ／ 二 角色 issue ／ 三 备案区 ／ 四 裁决记录汇总
- 填写规则：一行一条 ／ 场景列 ／ 业务背景与代号速查 ／ 同根因合并 ／ 依据类型 ／ 备案 ／ 摘引与代号 ／ 排序与编号

## 填写规则

- **一行一条 issue**：禁止回退为纯段落卡片；也禁止一行塞多条
- **标题必须自解释**：一句话说清问题本体（如「改名后缀在名称达上限时超长可致删除报错」），禁止以内部代号开头或堆叠代号
- **场景列必填**（分歧/角色/可测性明细表 + 裁决焦点表）：2-3 句业务白话（谁、在哪、做什么），禁止代号；裁决者不读 design/cases 可理解问题本体。素材 = 子代理产出的场景初稿（ARTIFACT 行为描述 + CONTRACT 章节），主会话 RECONCILE 时改写补齐——初稿前移，终稿裁判权在主会话
- **场景 good/bad 示例**：✅「运营在活动配置页勾选评选品类后点保存」——谁、在哪、做什么齐全；❌「setRange 提交 cellList 空报文」——代号不是场景
- **焦点表场景同源**：裁决焦点表「场景（白话）」列从对应明细行**原样复制**，不得改写（与标题列同源复制同口径，速览与明细同源）
- **业务背景行**：头部 kv「业务背景」2-3 句白话核心链路（谁→做什么→到哪），禁代号；生成时一次落盘，裁决阶段不追加内容
- **代号速查**：只列本文件实际引用的跨产物代号（防膨胀），一行一代号，释义为白话，来源列写定义处（如 digest §7 / design §4）；「编号体系」行只写命名规则（D/A/S/T 前缀与命名空间约定），具体代号释义全在速查节——禁止把释义塞回头部 kv 行
- **原文摘引强制**：「设计说」「用例说」「原文摘引」列必须引用 artifact 原文 ≤2 句 + 位置；**禁止只给行号/章节号不给原文**
- **单元格分行**：多口径、多段证据在单元格内用 `<br>` 分行；同一格内「口径」与「原文引用」分行书写
- **代号内联释义**：设计决策（设计.D-xx）、功能点（功能.F-xx）、待确认项（确认.Q-xx）、用例（用例.TC-xx）等他产物代号在行内首次出现时：①带命名空间前缀（禁止裸写 D6/TC-41 指代他产物——设计.D6 与本清单的 D-06 是两个东西）；②跟一句话说明（放标题或分歧点列），行须独立成立（速查节是集中导航，不豁免行内释义）
- **排序**：各表内按严重度降序（高→中→低→权衡），同级按编号升序；高严重度永远在每表头部
- **重点突出**：严重度列的「高」必须加粗（如 `**高**`、`**三·高**`、`**高**（记档）`），中/低/权衡不加粗——扫表时加粗行即重点，与裁决焦点表一一对应
- **速览必填**：统计表与裁决焦点表计数须与表格明细同源，明细是唯一权威
- **同根因合并（裁决单元）**：RECONCILE 过滤后、进清单前，同一根因多条（跨角色或单角色内）合并为一个裁决单元——主行进主责角色表（分层/契约→架构；表/字段/SQL→数据；覆盖/断言/可验性→可测性；两可归架构并在问题列注明）；主行「问题」列首句写根因，`<br>` 后写影响范围（命名空间引用，如 功能.F05 / 需求.FR-03 / 用例.TC-12）；场景列取主行场景（同根因通常同场景），被并入角色不再各写；其余角色证据并入主行摘引/问题列并标注来源角色；被并入条目不占编号、不留空行
- **依据类型**：「原文摘引」「设计说/用例说」列能给直接摘引 = hard；问题为缺失/未定义型、无直接原文可摘时，该列写「（无直接原文——依据：<一句推导链>）」= soft。soft 条目默认进批量预填组，不得单独进裁决焦点；**严重度=高的 soft 条目仍进焦点**（风险优先于不确定性）。代码定位（类名:行号）是附加证据，**不改 hard/soft 判定**（hard/soft 只看 artifact 原文可摘性）：RECONCILE 代码核对坐实的条目，代码定位写入「问题」（分歧清单为「分歧点/后果」）列作证据附注，合并主行置于影响范围之后（首句仍写根因，见「同根因合并」）；缺失型条目经代码坐实仍按 soft 计
- **备案**：严重度=低且建议为「无需动作/知悉即可」，或 RECONCILE 判「有效但纯观察」→ 备案区，沿用所属角色号段编号；不进裁决焦点、不需裁决、不参与放行闭环校验
- **合并示例（输入/输出对）**：输入——架构 A-03「驳回理由无长度上限校验」＋数据 S-07「驳回理由落库字段长度未定义」；输出——合并入架构表 A-03 行，问题列「驳回理由长度约束在设计与表结构两侧均未定义（根因）<br>影响：功能.F05 / 用例.TC-12」，摘引列并两角色证据并标（架构）（数据），S-07 不再占号
- 编号前缀固定：分歧 D / 架构 A / 数据 S / 可测性 T；跨轮不复用编号
- 严重度只有 高 / 中 / 低 三档；裁决为记档的条目严重度照写（高/中/低），由「裁决｜理由」列体现权衡语义
- 裁决列只填：`落改（<改动摘要>）` / `驳回：<理由>` / `存疑：<去向>`；由 sdlc-gate 会话在裁决时代填，生成时留空
- **落点/状态列**：裁决=落改的条目必填——`落点：<文件+位置> ｜ 待执行`，修订实际执行后改 `已执行`；驳回/存疑/权衡记档条目填 `—`。**放行前所有落改条目须为「已执行」**（Step 5 闭环校验，防批量组吞条目漏执行）
- 分歧清单永远置顶于角色 issue 之前——它是人工裁决的优先对象
- 裁决记录汇总用表格，一行一条；同主题批量裁决允许合并为分组行（编号区间 + 分组摘要），但**分组内的每条在明细表行上仍须有自己的裁决结果**（防批量吞条目）

## C 级自查清单（风险分级 C 时替代子代理扇出）

主会话强制套用 SKILL.md 对抗 prompt 逐项过（自查者与生成者同语境，独立性破坏已在头部「独立性」行如实标注）。对设计与用例两侧各过五问，命中即按宽表格式产出 issue（无命中写「无」）：

| # | 审查问 | 设计侧核对点 | 用例侧核对点 |
|---|---|---|---|
| 1 | 未言假设 | 设计断言中 PRD 未定义的口径（列出并标 soft） | 用例预期中无原文依据的取值 |
| 2 | 边界未处理 | 字段长度/数量上限/时间边界的处理方案 | 边界值用例覆盖或声明不生成（C 级仅 P0） |
| 3 | 契约违背 | 字段语义/接口行为与 §7 规则表口径一致 | 断言口径与规则表逐条对齐 |
| 4 | 存量兼容 | 展示/文案变更是否波及既有逻辑（发现影响面证据 → tier 只升不降，升级后改按 A 级扇出） | — |
| 5 | 不可逆改动 | 展示类功能中的删除/覆盖操作是否有确认 | 涉及删除/提交的用例不豁免（闭环不变量照常） |
