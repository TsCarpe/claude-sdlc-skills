# 需求体检维度体系（七层）

> 体检阶段的检查锚点。每项含：命中定义（通用模式）与严重度倾向。维度是启发式锚点而非封闭清单——发现维度外的问题也应记录，维度标注为「补充」。
>
> 第 1~6 层查文档内一致性（通读 + 模式匹配）；第 7 层查缺失类（判定基准在文档外，须先构造参照物——检查姿势见该层节首）。
>
> **严重度定义**：
> - **阻断**：不澄清该问题无法产出技术设计
> - **严重**：不澄清会导致技术设计做错
> - **建议**：顺带确认即可，不阻塞设计

## 第 1 层 概念层

最先执行：先从原文提取术语表，后续所有层以该术语表为基准。

| 检查项 | 命中定义（通用模式） | 严重度倾向 |
|---|---|---|
| 概念缺失 | 某概念/模块/对象被流程、规则或字段引用，但全文无定义、无对应功能入口（如：规则引用了某个"库/池/中心"，但该对象的来源与管理功能无任何需求） | 阻断 |
| 概念冗余 | 术语释义表中定义的概念，正文无任何落点 | 建议 |
| 概念模糊 | 定义存在但不可操作或不可判定。典型模式：①"系统自动 X"但 X 的判定条件无法落地；②"尽量/合理/适度"等无量化口径；③判定主体未指明（谁来判断） | 严重 |
| 术语不一致 | 同一概念在不同章节使用不同名称（状态名、对象名、操作名的同义异名） | 严重 |
| 术语污染 | 与本需求业务域无关的词汇残留，疑似从其他需求文档复制 | 建议 |
| 概念混淆 | 两个相似概念边界未区分（如：发起人 vs 参与人、单个产物 vs 汇总产物、两类名称相近的对象），导致归属规则无法判定 | 严重 |

## 第 2 层 状态机与流程层

对原文中每个带状态的对象（单据、流程实例、生命周期实体）分别检查。

| 检查项 | 命中定义 | 严重度倾向 |
|---|---|---|
| 状态不闭环 | 某状态无进入路径或无出口；对象进入某中间态后去向未定义；缺少终态 | 阻断 |
| 触发缺失/歧义 | 三种模式：①流转依赖的操作在功能清单中不存在（无入口按钮/无角色负责）；②自动触发条件不可判定（如"全部完成时"未定义完成口径）；③触发依赖的参数无处配置（如依赖"期限"但配置流程无此字段） | 阻断 |
| 流转冲突 | 两处流转规则互斥（如一处写"单向不可回退"，另一处写"可撤销重做"） | 阻断 |
| CRUD 不闭环 | 对象只定义了新增/提交的正向流程，缺修改、删除、取消、停用等反向操作，或反向操作规则不完整（谁能做、什么状态下能做、做完数据去哪） | 严重 |
| 在途数据未处理 | 阶段切换、截止时刻、配置变更时，存量数据与进行中操作的处置未定义（典型：截止瞬间正在提交的数据、流程配置变更后已按旧流程走的数据） | 阻断 |
| 配置×状态交叉 | 存在可配置项（流程环节开关、模式选择等）时，配置的不同取值与状态分支/流程形态的组合未展开定义（典型：某环节可选，但删掉该环节后状态机的对应分支未说明） | 阻断 |

## 第 3 层 数据与字段层

| 检查项 | 命中定义 | 严重度倾向 |
|---|---|---|
| 引用不存在的字段 | 展示或规则引用了字段 F，但 F 的录入项在表单/配置流程中不存在 | 阻断 |
| 计算依赖缺失 | 计算公式的输入字段在需求中不存在（公式引用了无处填写的值） | 阻断 |
| 计算口径未定义 | 有数值结果但规则不明：多来源数值如何汇总（平均/求和/去极值）、换算关系、满分、精度、保留位数 | 阻断 |
| 约束不一致 | 同一字段在两处的必填性、类型、长度、取值范围互相矛盾（注意功能清单与表单详述两处） | 严重 |
| 单位/制式歧义 | 同一数值存在多种制式选项（百分比 vs 分制、天 vs 小时）但无默认值、无配置者 | 严重 |

## 第 4 层 规则与逻辑层

| 检查项 | 命中定义 | 严重度倾向 |
|---|---|---|
| 规则冲突 | 两处业务规则互斥（同一操作在两处的允许条件/结果不一致） | 阻断 |
| 规则依赖缺失 | 有时限/SLA/阈值约束，但超时、越限后的处理未定义 | 严重 |
| 权限口径缺失 | 数据可见性/可操作性未按角色定义，或某角色对关键数据的可见性未说明 | 严重 |
| 边界值未定 | 数量上限、次数限制等写了"可配置"但无默认值；或上限触发后的行为只提示不定义 | 严重 |
| 优先级规则缺失 | 并列、同分、同时刻的排序/取舍规则未定义 | 建议 |
| 隐含约束未声明 | PRD 依赖但未写明的组织默认知识：幂等策略（重复提交期望）、权限边界（越权/撤销场景）、数据不出域、接口向后兼容等。信号词：「生成/提交/导出/分享」类功能背后未提及重复、越权、撤销行为。与第 7 层边界：本项管「业务默认知识未写明」（判定基准在组织常识内），第 7 层管「应参照外部文档而未参照」（判定基准在文档外） | 严重 |

## 第 5 层 角色与场景覆盖层

| 检查项 | 命中定义 | 严重度倾向 |
|---|---|---|
| 角色×功能缺口 | 某角色的功能只在清单/附录被提及，无详细需求（对照附录页面清单与正文详述逐项核对） | 阻断 |
| 清单-详述脱节 | 功能清单与详细描述条目对不上：清单有但详述缺失、详述有但清单缺失、两处同一条目的字段/操作不一致；序号断档 | 严重 |
| 原型-正文功能面缺口 | 已下载的原型附件与正文功能清单交叉核对：原型中的页面/功能入口/弹窗/字段在正文（含清单与详述）无任何对应 → 原型常代表产品真实意图，需确认是否漏写需求 | 严重（原型有正文无）/ 建议（反向：正文有原型无） |
| 通知矩阵缺失 | 状态变更、审核结果等事件×通知对象×通知渠道未系统化，仅零散提及"通知对方" | 建议 |
| 异常场景缺失 | 失败、超时、逾期、撤回、并发冲突等异常路径未覆盖（正向流程完备≠异常路径完备） | 严重 |
| 非功能性缺失 | 容量、性能、留痕、归档、审计等未提及（存在大文件上传、批量操作、外发内容时尤甚） | 建议 |
| 编辑影响未定义 | 声明某状态/阶段可编辑，但编辑对已产生数据（已流转记录、已计算结果）的影响未说明 | 严重 |

## 第 6 层 文档质量层

多为低严重度，但删除不彻底与自相矛盾会实质性误导设计。

| 检查项 | 命中定义 | 严重度倾向 |
|---|---|---|
| 删除不彻底 | 某功能被标记删除/划线，但其他章节（清单、详述、状态流转、关键词表）仍引用——需确认该功能的最终去留 | 严重 |
| 自相矛盾段落 | 文档内两段陈述直接互斥（同一状态/操作两处描述相反） | 阻断 |
| 待确认与正文脱节 | 正文已写死规则，"待确认事项"中仍在问同一问题——以哪个为准 | 建议 |
| 外部依赖未附 | 原型/附件指向文档外部资源，或内嵌附件下载失败（输入读取记「未读取（原因）」），评审时内容不可得——此时第 5 层「原型-正文功能面缺口」不可执行，描述中需一并说明 | 建议 |
| 编号低错 | 序号断档、空值单元格、格式残缺、修订记录与正文不匹配 | 建议 |
| 评论结论未同步正文 | 评论答复已形成结论/变更口径（梳理按评论提取），但正文对应章节未同步修订——**修订型**（答复表达了对被答复条目的更新，如「改为/更新为 Y」）停 🔵；**升级规则**：评论结论与**未被该答复覆盖的**其他正文规则或其他评论结论实质性互斥（同对象同维度不同取值/不同操作，且不构成"旧版→新版"的修订关系——如答复「X 无需确认」与另一章节「所有同类操作均需确认」的总规则矛盾而答复未表达修订该总规则）时升 🟡 并标注「源间冲突待裁决」——梳理阶段可按最新评论口径转述被答复条目，但体检不得静默择一，两处口径都写进命中交 PM 裁决 | 建议（非修订型互斥升级严重） |

## 第 7 层 外部参照层

缺失类检查——本层检查项的共同语义是「判定基准在文档之外，需先构造参照物（平行结构、数据血缘、消费关系、外部系统）再拿文档去对」。

**输入优先级**：本层是三类候选的汇流判定层——①存在 `refs-<日期>.md`（体检阶段 0 参照表产物，构造规范见 [ref-tables.md](ref-tables.md)）时，优先消费其候选清单，成立的命中标来源 **D1**；②阶段1 视角推导候选（任务卡见 [perspectives.md](perspectives.md)，仅 A 级需求）标 **D2**；③无表无候选时按下列构造姿势直接推导，命中标 **D3**。三路同根因时合并为一条、标 D1（证据最硬）；D2 候选判定时沿用本层证据要求与降级纪律。

构造姿势：

- **平行结构识别**：文档自身声明的同类并列结构（同模板重复的并列章节、同一字段的多枚举值、多角色/多端/多租户/多组别），拉「维度值 × 功能面」矩阵对照——识别定义必须用中性虚构例子（如"评选活动分甲/乙/丙三个组别并列描述"），不得绑定某具体业务的叫法
- **消费关系闭包**：对每个被录入/维护的字段问"谁消费它"；对每个被计算/展示的输入问"它从哪录入"
- **来源追溯**：对每个被依赖的对象/数据问"它如何进入系统"（本系统录入 / 导入 / 外部同步，三者皆无即无源）

| 检查项 | 命中定义（通用模式） | 严重度倾向 | 证据要求 |
|---|---|---|---|
| 有录无消 | 某字段/属性存在录入或维护入口，但全文无任何计算、展示、规则、导出消费它（反向闭包为空）。虚构例：活动档案维护「机构类型」字段，但报名、评审、报表全文均未使用该字段 | 严重（须附证据，否则降建议） | 必须列出该字段全文出现位置清单，并逐处说明为何不构成消费方；消费方疑似在本文档范围外（姊妹文档/后续版本）时降 🔵 且改问式「该字段的使用方是什么？」 |
| 有消无录 | 计算公式、展示列或规则引用了某输入值，但该值的录入项、配置入口、划线/阈值设置在全文无处存在。虚构例：报表按「入围率」统计，但全文无任何入围线（阈值）的配置入口 | 阻断 | 列出全部引用处（章节+引文），并说明已检索过配置类章节无对应入口 |
| 数据无源 | 某对象/数据被流程或计算依赖，但其来源与进入系统的入口无定义（既非本系统录入、也非导入、也未声明外部同步）。虚构例：评审规则依赖「上一年度终评名单」，该名单从哪场活动/哪个系统进入本文档所在系统无任何说明 | 阻断 | 列出依赖处 + 已核对无入口的说明；正文确有来源但表述含糊时归第 3 层「计算依赖缺失」不重复报 |
| 引用断链 | 正文以「下文另行说明」「如上所述」等指引指向的内容无落点；或某板块/规则被多处引用却无定义章节。虚构例：「报告含入围对比、贡献分析、名单三个板块（各板块内容下文另行说明）」，下文无任何对应章节 | 严重 | 引用原句 + 全文检索无落点的说明 |
| 对称缺格 | 平行结构的某成员缺少其兄弟成员具备的功能面/配置项/报告板块，且该成员的业务逻辑同样需要它。虚构例：甲/乙两组别并列描述统计设置，甲组有「入围线划线」设置而乙组无，而乙组报告同样计算入围率 | 阻断 | 先点明并列结构本身（哪些章节/枚举构成对称），再列缺格矩阵；正文显式声明差异为有意设计（如"本组别不含 X 功能"）的不命中 |
| 跨模块不对齐 | 模块 A 定义的集合/枚举与模块 B 消费的集合之间，匹配、校验或对齐规则未定义——A 的数据进 B 时冲突/缺失/多余怎么办。虚构例：报名模块按「赛区」收集机构，对比模块选两届活动做对比，两届参赛机构不一致时以哪届为主键、缺失机构怎么展示，全文未定义 | 严重 | 点明两侧集合各自的定义处 + 未定义的对齐场景 |

**本层严重度纪律（覆盖全局从严规则）**：从严适用于**是否记录**（拿不准是否缺失时，记录并注明不确定），不适用于级别——拿不准阻断还是严重时**降一级**并在描述中说明原因。理由：缺失类判断的依据在文档之外，不确定性天然更高，按全局从严推高级别会把最不确定的判断灌进 PM 的必须确认档。

## 检查顺序与使用说明

1. **顺序固定**：1 概念 → 2 状态机与流程 → 3 数据与字段 → 4 规则与逻辑 → 5 角色与场景覆盖 → 6 文档质量 → 7 外部参照。概念层的术语表是第 2、3 层的判定基准（术语不一致会放大为字段/状态矛盾）。
2. **逐层产出**：每层检查完记录命中项（维度/检查项/原文定位/引文），再进入下一层；层间发现新术语问题回写术语表。
3. **每条命中必须附原文定位**（章节或评论区 + 原句引用）。缺失类命中无原文可引时，定位写「全文未见 X」+ 最接近的关联章节（详见 report-template 撰写规则）。
4. **严重度从严**：拿不准标高一级，并在描述中说明不确定原因。**第 7 层例外**：该层从严适用于是否记录、不适用于级别，拿不准级别时降一级并注明（见第 7 层节末纪律）。
5. **去重合并**：同一根因在多层命中时合并为一条，维度标主责层，描述中提及关联层。**第 7 层回写**：本层命中若推翻前层结论（如某「清单-详述脱节」实为整板块缺失、某第 3 层「计算依赖缺失」实为配置项整体缺失），按本条合并规则回写对应层明细，不双报。
6. **严重度升级同步**：实际上下文允许偏离「严重度倾向」（如文档质量问题牵动状态机终态时上调），但**明细表的级别是唯一权威**——阻断速览的收录、第 1 章统计表计数、PM 清单分级计数必须全部与明细级一致。禁止「列入速览但明细级仍为原级」的中间态；速览只收明细级为 🔴 的条目。
7. **决策类型标注（C 约束 / H 假设）**：规则类/决策类命中在报告明细表「类型」列标注，与状态列正交（类型=问题定性，状态=处理进度）。判定口诀：**「这条被推翻时，是事故还是改进？」**——事故（重复提交产生两条记录）→ C 约束；改进（缓存 TTL 从 5 分钟调到 30 分钟）→ H 假设。体检产出时标初判 `C?` / `H?`，纯澄清类问题（入口在哪、术语含义）标 `—`，拿不准也标 `—`；PM 答复后去问号定型。**流转落点**：定型 C → 人工持体检报告调 sdlc-guardrails skill 按候选编写规则（自动检查是约束的归宿）；定型 H → 转测试验证项，澄清要「方案+接受条件」而非唯一答案。**H 永不进护栏**（把假设锁死进规则违反其本意）；H 被事实验证后毕业为 C 或换新 H。列值域与措辞规范见 report-template 撰写规则。
