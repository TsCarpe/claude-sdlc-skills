## 2. 四角度摘要

### 角度一：三案例的共同演进曲线

超级个体（1 人指挥 3-5 会话，产能锁在个人电脑）→ 数字员工（云上运行、统一结构输出，但岗位孤立、质量不稳）→ 云上协作（按业务域组织数字员工 + 共享技能，人收拢到 **Loop 维护 + 寻找真需求**）。关键坦白——超级个体期的两个障碍正是多数团队当前所处阶段：

- **消化障碍**：Token 产出中间产物，理解/评审/应用靠人完成跟不上
- **复用障碍**：会话沉淀的知识靠 Skill 团队级复用并不容易

量化结果（千问用增，3 个月）：交付周期缩短一半、千行代码缺陷率降 70%、变更失败率降 90%+（p08）。万有无界：线上千行缺陷率 0.01‰、视觉缺陷 auto-fix 一次成功率 89%、协作工作区 30+ 共享技能 + 8 类专项工作流调用 2 万次（p13-14）。

### 角度二：五大挑战中三个刺人的判断

1. **「Coding 正在被解决，主战场迁移到验证与环境」**（p16-19）——价值占比预测：编码 2024 年 50-60% → 2027+ 5-10%；环境与验证 10-15% → 40-50%。电气化类比：把 AI 嵌入既有流程 = "电力轴传动"（只换动力源不重组产线）；**Agentic 的核心不是 AI 有更多决策权，而是它能自主获得验证信号并据此持续推进**——Workflow 只管调度/权限/审计/高风险检查，不管 Agent 怎么思考（p18）
2. **「度量对象从工具使用量转向生产系统运行质量」**（p22-26）——L1 AI 效能 → L2 工程质量 → L3 价值交付三层证据链；**上下文资产（Skill/MCP/Spec/runbook/checklist）是被低估的度量对象**："不度量这些资产，团队就停留在每个人临时问 AI 的阶段"（p26）
3. **「10x 是组织指标，不是个人指标」**（p29-32）——考核从产出规模（代码量/工单数）转向任务结果与系统化收益；协调成本没有消失，而是转移到目标定义、任务拆解、验证标准、发布门禁

### 角度三：基础设施七大件

Harness（模型网关 + 接入层五能力：测活/权限卡点/环境预检/审计/语境注入）→ 企业知识库（面向 Agent 的组织记忆：任务为中心/三路召回/版本置信度/MCP Server 化）→ 工具体系（MCP 连接治理 / Skill 复杂流程 / CLI 标准动作；**Skill 生命周期：创建→发布→观测→反馈→淘汰**）→ Sandbox（隔离/临时/可审计，L1 进程级→L4 VM）→ Identity & Policy（agent_id+principal+runtime 三元组、Credential Broker、渐进式授权）→ Guardrail（四层：L1 输入过滤/L2 执行卡点/L3 输出过滤/L4 行为审计；**写时拦截 > 事后审计，但护栏不是越多越好**）→ 可观测（Trace 四层结构 Session→Task→Step→ToolCall；采集→处理→分析→**反哺**闭环）。

### 角度四：与前三家（本仓 guide.md）的差异

手册与三家理论高度共振（瓶颈转移、上下文工程、验证成核心技艺），但补上了三块：

| 手册独有 | 内容 | 页码 |
|---|---|---|
| 失败模式坦白 | 超级个体的消化/复用障碍、数字员工的质量不稳（验收功夫不比执行省下的少）——从 0 到云上协作之间真实的坑 | p02, p26 |
| 数据闭环业务侧用法 | 技术上成立 ≠ 业务上做对：上线后按执行漏斗分层评测定位 bad case 再补能力，80% 核心能力 Skill 化 | p04 |
| 企业身份/权限/审计 | Agent 同时踩中人/应用/服务账号三类主体边界；"权限设计最难的不是鉴权技术，而是主体模型变了" | p27-28 |

## 3. 与本仓现状的对照结论

**已对齐**：需求前置澄清（sdlc-intent 两段式 + 澄清闭环比手册案例更系统——块级锚点/双向追溯）；人在关口裁决（sdlc-gate 同构）；AI 产物不直写正式数据（平台草稿两态 = 手册"写时拦截"）；验证左移（sdlc-test 闭环不变量方向正确）。

**核心结论**：手册挑战一与 [ai-native-sdlc-guide.md](ai-native-sdlc-guide.md) §7 自我诊断**独立得出同一判断**——验证与环境是主战场、短板在 Test/Deploy 右侧。两个独立信源（海外理论三家 + 阿里一线案例）指向同一方向，**sdlc-test 的投入优先级高于继续加需求侧规范文档**。

## 6. sdlc-platform roadmap（仅建议，不涉该仓改动）

按性价比排序，均与平台既有"未做钩子"对得上：

1. **执行证据上链**（平台未做清单 #8 提前）：把 sdlc-test exec 的截图/trace 经 media 端点上链，需求详情页加证据区块——平台从"文档协作面"升级为"事实与证据面"（手册语境里上下文资产 = 文档+工程+证据三类，平台现只有第一类）；本次 P1-2 的证据索引是它的数据源
2. **度量微缩版**：task 表 + clarify_item 答复时间戳 + 发布时间戳天然构成归因链（质检耗时→澄清周转→发布周期），verify 脚本加 metrics 聚合即可，不必建指标系统（"度量反向塑造研发流程"——澄清答复时长分布能暴露 PM 卡点）
3. **Agent Registry 微缩**：通道 B 的 agent 已有 pause/resume，补"哪个 agent 代表谁、干过哪些任务、成功率"的登记面（手册：审计要看清是人在操作还是 Agent 在操作）
4. **事件驱动触发**（未做 #3）：L2 编排已是确定性事件钩子、方向正确；自然延伸是飞书通知 + 机器人监听，把人肉盯网页从 Loop 去掉——优先级用 2 的数据说话
5. **guardrails 平台化候选**：三个本地 skill 中它最值得下一个平台化（确定性机制不需要 agent；平台侧对等物 = 任务执行前 guard 检查 + selfCheck 扩展）
6. **谨慎项**：Sandbox/多租户/身份体系是万人组织的问题，单维护者内网场景保持"钩子按需启用"纪律本身即手册"护栏不是越多越好"的践行

两处增量信息：平台 UI 原型演化线沉淀在本仓 `platform-demo/`（gitignored、未随仓库发布；两仓耦合比 README 声称的"代码级零耦合"多这条设计资产线）；进程内 AgentScope 通道已跑通（`verify-agent.mjs`，属 sdlc-platform 仓），通道 B 由此获得真实任务数据——它是方向 2/3 的前置。
