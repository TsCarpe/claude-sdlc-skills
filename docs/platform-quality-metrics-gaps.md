## 一、机检脚本缺陷（先修误报，再补盲区）

### #1 `p-coverage` 把 `体检.Pxx` 误判为幽灵 P 号（P0 · 误报）

- **文件**：`skills/sdlc-sync/scripts/check_standard_doc.py:179`
- **现状**：
  ```python
  body_tags = set(re.findall(r"〔?P(\d{1,3})", self.body))
  ```
  正则只要求前面**可有可无** `〔`，因此 `体检.P22` 中的 `P22` 也被计入正文 P 号集合；附录 A 只登记裸 `P01~P20`，于是报出幽灵号并在退出码 1 上直接 FAIL。本定稿实跑报 6 个（`P22/23/25/26/29/30`，其余 `P21/24/27/28` 只出现在附录 B 之后、不在扫描的正文段内；全文档扫描口径下是 10 个 `P21~P30`）。
- **根因有两处**，只加后顾断言不够：① `体检.Pxx` 前缀；② `体检.P01~P30` 区间写法与 `体检.P18、P19、P30` 顿号续列——后者不带 `体检.` 前缀，裸扫时仍会被当成裸 P 号。
- **目标**：先剥离体检编号段（含区间与续列），再做裸 P 号扫描：
  ```python
  def strip_audit_refs(d: str) -> str:
      d = re.sub(r"体检\.P\d+(?:\s*[、,，/]?\s*[~-]\s*P?\d+)?(?:\s*[、,，/]\s*P?\d+)*", "", d)
      return re.sub(r"(?<![.．A-Za-z0-9])P\d+\s*[~-]\s*P?\d+", "", d)
  body_tags = set(re.findall(r"(?<![.．A-Za-z0-9])(?:〔)?P(\d{1,3})", strip_audit_refs(self.body)))
  ```
- **验收**（已用本定稿实测，建议直接作为回归断言）：
  - 真实文档：幽灵号 0、附录 A 的 P01~P20 全部有落点（missing 0）；
  - 注入 `〔P21〕` → 报 21；注入裸 `P23。` → 报 23；注入 `〔P24〕 又见 P25` → 报 24、25。
  - 三项都要验证，防止「修成永真」。

### #2 `p-semantic` 把「影响范围标注」当条款语义（P1 · 噪声）

- **文件**：同文件 `:303-323`
- **现状**：1.2 范围清单是长句 bullet，如
  `1. 活动检查列表优化：…、联评活动记录「联评范围」列与操作区〔P07〕。`
  该处是「哪些条款受 P07 影响」的登记，不是条款本身，字符重叠率天然低，6 条 WARN 全来自这里。
- **目标**：增加一条减噪——同一行出现 **≥2 个** `〔Pxx〕` 标记，或该行位于「本期范围/不做/边界」语义的列表内时，跳过语义抽查（这些是多对多登记行）：
  ```python
  if len(re.findall(r"〔P\d{1,3}", line)) >= 2:
      continue
  ```
- **验收**：本定稿 `p-semantic` WARN 从 6 降到 0~1；真错挂样本（把 P03 的结论挂在讲「模板大小」的条款上）仍触发 WARN。

### #3 `count-assert` 把原文引述语当计数断言（P1 · 噪声）

- **文件**：同文件 `:231-276`
- **现状**：`（仅一条 vs 已关联 2 条/共 5 条 vs 三来源）`、`资源分类口径三类/五类不一致` 等**引述原文缺陷描述**的短语被当作「N 条」断言，去数后续表体得到 30/12/7 行，报不符。
- **目标**：断言语境排除以下三类——① 位于 `「」`/`（）` 引述内；② 紧邻 `vs`、`/`、`或` 的并列枚举；③ 同行含 `原文`、`不一致`、`口径` 等元描述词。
- **验收**：本定稿 `count-assert` 剩余命中 ≤2 且逐条可解释；构造真计数错误（写「含五类维度」却列 4 条）时仍命中。

### #4 `strike-vs-appendixc` 只对账数量，不对账条目（P1 · 半真）

- **文件**：同文件 `:210-229`
- **现状**：只比 `正文删除线数 vs 附录 C 行数`，容差 ±2 判 PASS。本定稿 12 vs 15 触发 WARN，但真正的问题是**附录 C 第 5/12/14 条在正文没有对应删除线**（「仅一条」「3.c 整段」「评论 c19」三条只在附录登记）。数量容差恰好把「登记了但正文没标」的结构性缺陷混同于「多处标记对应一条登记」的正常情况。
- **目标**：改为双向对账——附录 C 每行的「废弃内容」取前 8 字，必须在正文 `~~…~~` 中命中一次（归一化后子串匹配）；未命中则 FAIL 级明细列出行号。
- **验收**：本定稿报出第 5/12/14 条未标注（3 行明细）；把标记补齐后 PASS。

### #7 新增 `self-contained`（P0 · 盲区，最高优先）

- **文件**：同上

## 二、平台侧度量缺口（`sdlc-platform`）

### #11 publish 门槛把「挂起」计为「已答复」（P0 · 门禁失效）

- **位置**：`sdlc-sync/SKILL.md:122` `仅当平台显示全部问题已答复（answered == totalQ）`；平台 `card.answeredQ / totalQ` 统计。
- **现状**：`REQ-2026-044` 的 `answeredQ=20, totalQ=20` → 允许发布，但 `items` 里 **P12 的 status 是 `deferred`（无答复）**，且 P12 覆盖「谁可认领/全局替换他人署名」「评审录音与榜单草稿对谁可见」两项敏感权限。挂起项被计入已答复，权限未定案仍发布了定稿。
- **目标**：① `answeredQ` 只统计 `status == answered`；`deferred` 单列 `deferredQ`；② publish 门槛改为 `answeredQ == totalQ` 仍保留，但**红级（red）条目存在 deferred 时硬拒**，黄级 deferred 需前端二次确认并写入发布记录的 `pendingAssumptions`。
- **验收**：以本卡为回归——P12 为黄级 deferred，发布时应弹「1 项挂起将进入遗留假设，是否继续」，发布记录含 `pendingAssumptions: ["P12"]`；人为把 P12 置为红级则发布被拒。

### #12 定稿缺独立质量评分（P1）

- **位置**：`iterations` / `requirements` 的 `quality: {stars, basis}`。
- **现状**：`v3.8.0-5` 的 `quality` 为 `{stars: 1, basis: "阻断 10 项"}`，这是**原文体检**得分；定稿（standard）没有任何独立评分或机检结果落库。同一界面 `tab=std` 展示定稿，却沿用原文的低分，读者会误读。
- **目标**：产物级评分——`quality.byArtifact = {intake: {…}, standard: {machineCheck: {fail, warn}, specCompliance: {…}}}`；`tab=std` 页头展示定稿自己的机检通过态（如 `机检 FAIL 0 / WARN 2 · 头部合规`），不复用原文星级。
- **验收**：本定稿在页面上显示自身机检结果（FAIL 1 → 修 #1 后 0）；原文星级与定稿质量分在同一页面可区分。

### #13 覆盖率 0/56 与文档质量混淆（P1）

- **位置**：`coverage.forward = {covered: 0, total: 56, pct: 0.0}`；`backward.pct = null`。
- **现状**：该数值由「用例是否引用 FR」计算，`caseCount=0` 故为 0。它是**测试覆盖**指标，不是文档质量指标，但展示在定稿页附近容易被当作「文档 0 分」。
- **目标**：拆成两个指标并改名——`docRuleCoverage`（每条 FR 在正文有落点，由 §D 索引 + 机检 `fr-continuity` 得出，本卡应为 56/56）与 `caseCoverage`（用例引用率，本卡 0/56）。未建用例时 `caseCoverage` 显示「—（未建用例）」而非 `0%`。
- **验收**：本卡 `docRuleCoverage=100%`、`caseCoverage=—`。

### #14 假设项闭环率未成为门禁指标（P1）

- **位置**：`card` 无假设统计字段；定稿十三「遗留假设 7 条」仅在正文里。
- **现状**：定稿自报 A01~A07 七条假设，机检 `a-registry` 报 A05 正文未引用。核心工程（gate / 开发入口）读不到「本需求有 7 条未定案假设」这个事实。
- **目标**：`doc.standard.content` 增 `assumptions: [{id, status, owner, due}]`，平台展示「遗留假设 7 · 未定案 7」；`pull-dev-bundle` 时缺省把未定案假设连同 design 一起投影给开发入口。
- **验收**：本卡十三章被解析成 7 条结构化假设；A05 的「正文无落点」在平台可见。

### #15 真实媒体与统计口径（P2）

- **现状**：定稿头部写「媒体 56 件」，平台 `doc.media` 实为 55 条；56 = 块数（49 image + 3 whiteboard + 4 attachment）。
- **目标**：平台向合成端提供**已去重**的媒体计数与块类型分布（含 whiteboard/image 未文本化告警），合成端禁止手写统计值（与 #5 联动）。
- **验收**：头部不再出现统计值；平台侧提供 `media.unique=55 / blocks=56 / untextualized=[whiteboard×3]`。

## 四、本轮决策记录

1. **机检 FAIL 是硬门禁，不是度量**：publish 侧机检 fail>0 一律 400 拒发，`confirmed` 不放行（文档缺陷不是取舍，与挂起的「可确认放行」刻意区别）；机检降级（脚本缺失/旧副本）仍放行——脚本不可用不是文档的错，由 Dockerfile 构建期金丝雀兜住副本漂移。取舍：挂起门禁保护「未定案的产品决策」，机检门禁保护「文档自身缺陷」，两者分级不同故处置不同。
2. **confirmNote 必填**：黄/蓝挂起确认重发必须携带放行理由（空即 400）——与平台变更单「确认人留痕必填」同基调；发布是更重的终态动作，留白不可接受。
3. **挂起确认前置分流**：skill 侧 publish 流程先读 `deferredQ`/`items` 分流（红级即停、黄蓝列清单确认），409 退化为并发兜底——避免红级挂起白做一轮合成+机检后才被叫停。
