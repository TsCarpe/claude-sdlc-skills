 # AI 替代人工测试方案（sdlc-test 设计决策记录）

> 版本：v0.2（细化：工具选型论证 + 测试设计方法论 + skill 子命令化组织）
> 日期：2026-09-02 定稿，2026-09-12 随开源整理（skill 现名 sdlc-test，文中 ai-test 为历史名）
> 关联：[sdlc-test skill](../skills/sdlc-test/SKILL.md)、[workflow.md](workflow.md)（全流程叙述）、`sdlc/<需求名>/intake/*`（需求梳理三件套，sdlc-intent 产出）

---

## 1. 背景与目标

**现状**：所在项目（某 Java DDD 业务系统）仓库零自动化测试，质量保障完全依赖人工测试——测试人员拿需求文档/原型，在 test 环境通过前端页面操作，执行新功能验收与老功能回归，接口层较少直接测。

**目标**：用 AI 测试智能体承接人工测试的**执行**工作。核心工作流程不变（用例设计 → 执行 → 结果判定 → 缺陷反馈），执行主体从人转为 AI；人退守两道关卡（用例审核、报告复验）。

**业界定位**：本方案属于 Agentic Manual Testing 范式（computer-use 智能体像人工测试员一样现场执行测试），但以 Claude Code + MCP 自建 Harness 实现，且叠加了人工测试员不具备的**静态代码分析**能力（需求 ↔ 实现一致性比对）。

---

## 2. 人工测试员 vs AI 测试智能体：能力对比

| 维度 | 人工测试员 | AI 测试智能体 |
|---|---|---|
| 信息摄入 | 需求文档/原型，靠阅读理解 | 需求文档 + YApi 接口契约 + 数据库 schema + **全量源码** |
| 操作执行 | 浏览器点击，速度受限于手 | chrome-devtools/Playwright 驱动浏览器，速度受限于推理与页面加载 |
| 结果判定 | 凭需求理解和经验 | 预期显式来自用例；实际可交叉验证**页面 + 接口响应 + MySQL 落库**三方证据 |
| **静态代码分析** | ✗ 做不到 | ✓ 需求规则 ↔ 实现逻辑逐条比对（Controller/Service/Mapper 链路），**AI 独有增量能力** |
| 跨角色流程 | 手动切换账号 | 多账号自动切换（isolatedContext 会话隔离） |
| 回归复测 | 疲劳、遗漏、成本高 | 存量用例机械复跑，零疲劳 |
| 探索性/可用性判断 | ✓ 强 | ✗ 弱（视觉审美、交互手感不可靠） |
| 误判风险 | 有 | 有（可能误报/漏报）；靠三方证据交叉验证 + 人工复验关卡压制 |
| 成本 | 人力线性 | token 成本，随用例量线性 |

**结论**：AI 可替代的部分——用例生成、脚本化执行、判定、回归复跑；不可替代的部分——用例质量把关、报告复验、探索性/可用性判断。方案据此设计两道人工关卡。

## 3. 总体架构：四阶段编排 + 两道人工关卡

```
需求文档（sdlc/<需求名>/intake/ 三件套优先）
      │
      ▼ 阶段1 用例生成（信息摄入：需求文档 + YApi 契约 + CodeGraph 只读辅助）
轻量用例 checklist → sdlc/<需求名>/test/cases.md
      │
      ▼ 🔒 人工关卡1：用例审核（强制暂停，迭代修改直至确认）
      │
      ▼ 阶段2 静态代码检测（需求 ↔ 实现一致性比对，先于功能测试）
      │    产出：✅符合 / ⚠️疑似偏差[附代码位置] / ❓静态无法确认
      │    疑似偏差 → 作为阶段3重点验证项
      │
      ▼ 阶段3 前端功能测试（chrome-devtools 操作 test 环境，逐用例执行）
      │    判定证据：页面表现 + 接口响应 + MySQL 落库 + console 异常（补充）
      │
      ▼ 阶段4 报告生成 → sdlc/<需求名>/test/reports/<日期>-r<N>/report.md
      │
      ▼ 🔒 人工关卡2：报告复验（确认缺陷真伪 → 人转达开发）
```

### 3.1 阶段1：用例生成

- **输入**：需求文档路径 + 测试范围说明
- **信息摄入**（只读，让用例更准）：
  - `sdlc/<需求名>/intake/` 需求梳理三件套（**首选输入源，优先于原始 PRD**）：梳理文档中的角色权限矩阵、状态机图、业务主流程图、规则口径清单是测试设计的直接输入；体检报告的疑似问题点直接转为重点用例；PM 清单已澄清的口径回填用例预期
  - YApi MCP：接口契约、出入参
  - CodeGraph MCP：定位相关 Controller/Service，理解系统实际行为
  - MySQL MCP（只读）：表结构、枚举值（等价类划分与边界值分析的依据）
- **设计方法论锚点（强制）**：用例必须显式运用结构化测试设计技术，禁止泛泛罗列操作步骤。业界共识：LLM 泛泛生成的用例质量平庸，质量取决于是否显式指定设计技术。技术清单与适用场景见 skill 的 `references/cases/design-techniques.md`：
  1. **等价类划分**：有效/无效等价类，各取代表值
  2. **边界值分析**：上点/内点/离点（数值、长度、日期、次数上限）
  3. **判定表**：多条件组合规则（如"角色 × 状态 × 时限"组合出的不同处理）
  4. **状态迁移覆盖**：梳理文档每条状态机迁移边至少一例，含非法迁移尝试
  5. **场景法**：基本流 + 备选流 + 异常流（对应梳理文档的业务主流程图）
  6. **错误推测**：重复提交 / 越权访问 / 并发操作 / 必填缺失 / 格式非法
- **覆盖度自检（双向追踪）**：用例文件内维护"需求规则条目 ↔ 用例 ID"映射表；无用例覆盖的规则条目必须显式列出并注明原因（豁免/待补充）。这是关卡 1 人工审核的核心抓手，也是压制漏报（方案最大风险）的唯一手段
- **产出**：`sdlc/<需求名>/test/cases.md`，结构见 `references/cases/case-template.md`：头部元数据（审核状态 + 阶段进度 checklist）/ 设计技术覆盖矩阵 / 双向追踪表 / 用例总览 / 用例明细（TC 小节，含"设计技术"标注）

### 3.2 人工关卡1：用例审核（强制）

1. 用例生成后 **暂停**，向用户展示用例清单摘要 + 文件路径
2. 用户直接读文件（或 git diff）审核，反馈修改意见（增/删/改/调优先级）
3. 迭代修改 → 再次展示 → 直到用户明确确认
4. 用例文件头部记录审核状态：`草稿` → `已确认（日期）`

### 3.3 阶段2：静态代码检测（先于功能测试）

**这是 AI 相对人工测试员的核心增量能力**，且安排在功能测试之前——静态发现的疑似偏差直接变成功能测试的重点验证项，重大偏差可提前反馈。

方法：
1. 从需求文档逐条提取业务规则（校验规则/状态流转/权限/字段口径）
2. CodeGraph 定位每条规则的实现链路（Controller → Service → Mapper/XML）
3. 逐条比对：实现逻辑与需求描述是否一致
4. MySQL MCP 核对表结构与需求字段

产出：静态检测发现清单，三态标注——
- ✅ 符合（实现与需求一致，附代码位置）
- ⚠️ 疑似偏差（实现与需求描述不符，附代码位置与差异说明）
- ❓ 静态无法确认（需功能测试验证）

### 3.4 阶段3：前端功能测试

- **工具**：chrome-devtools MCP
  - `new_page` / `navigate_page`：打开 test 环境（URL 来自 `sdlc/env/test.md`）
  - `take_snapshot`：a11y 快照定位元素
  - `fill` / `fill_form` / `click`：执行操作（登录账号来自 `sdlc/env/accounts.local.md`，账号密码直登）
  - `take_screenshot`：执行证据
  - `list_network_requests` / `get_network_request`：接口实际响应
- **判定证据**：页面表现 + 接口响应 + MySQL 落库（MySQL MCP 查证），三方为主；**console 异常为补充证据**——每个用例执行后 `list_console_messages` 检查 JS 报错，即使功能表象正常，页面报错也标记为疑似缺陷
- **造数策略**：前置数据优先通过前端页面跨角色操作构造（与真实链路一致，顺带覆盖跨角色流程）；MySQL MCP 只读、仅做落库核验，**禁止直接改库造数**
- **跨角色流程**：多账号切换（登出重登或 isolatedContext 隔离会话）
- **结果回填**：用例文件回填执行结果（通过/失败/阻塞），截图落 `screenshots/`

### 3.5 人工关卡2：报告复验

报告生成后**暂停**，用户复验缺陷真伪；确认后的缺陷由**人**转达开发（缺陷不自动推送飞书/bug 系统）。

### 3.6 工具映射表（全部本机已有，零新建基础设施）

| 环节 | 工具 | 用途 |
|---|---|---|
| 需求摄入 | Read（sdlc/<需求名>/intake/*） | 需求文档/梳理三件套 |
| 接口契约 | YApi MCP | 接口定义、出入参 |
| 代码定位/理解 | CodeGraph MCP | 符号/调用链/影响面 |
| 数据核验 | MySQL MCP（只读） | 表结构、落库校验 |
| 浏览器执行 | chrome-devtools MCP | 导航/快照/操作/截图/网络请求/console 消息 |
| 浏览器兜底 | Playwright skill | chrome-devtools 失效时降级 |
| 缺陷定位辅助 | ES 日志检索 / Sentry MCP | 报错日志、异常堆栈 |
| 持久化 | 本地文件（sdlc/ 目录） | 用例、报告、证据 |

**选型否决记录**（评估过但不引入，避免后续重复调研）：

- **gitnexus**（2026-08-28 本机实测后卸载）：与 CodeGraph 同类（Tree-sitter 解析 + 本地知识图谱 + MCP），无测试场景增量能力，且实测存在正确性缺陷——枚举静态访问无图边，impact 分析返回 0 影响面的错误结论
- **Skyvern / browser-use / Stagehand**：独立浏览器智能体框架，与 Claude Code 叠加形成双层 agent（agent 套 agent），编排不可控、调试困难，放弃
- **Microsoft Playwright MCP**：偏自动化操作，无网络请求/console 回读能力，无法支撑证据判定，不作为主执行器
- **QA Wolf / QA.tech / Wopee 等商用测试 SaaS**：与自建 Harness 路线冲突，且引入外部依赖

报告结构：执行摘要 / 静态检测发现 / 功能测试结果 / 缺陷清单（预期/实际/复现步骤/疑似代码位置/截图引用）/ 用例覆盖度。

## 5. 能力沉淀：skill `sdlc-test`（主 skill 路由 + 阶段独立可重入）

sdlc-intent 的"阶段式暂停等人"模式保留，但测试周期远长于需求梳理（可能跨会话、执行阶段可能中断），单 skill 连跑的会话内暂停不够用。因此采用**四个子命令各自独立可跑可重入，主 SKILL.md 负责路由与编排**：

```
skills/sdlc-test/
  SKILL.md                    # 子命令路由 + 四阶段编排 + 两道关卡规则
  references/
    design-techniques.md      # 测试设计方法论锚点（六种设计技术 + 可读性硬规则）
    case-template.md          # 用例文件模板（含覆盖矩阵 + 双向追踪表 + 缺陷跟踪）
    static-check-template.md  # 静态检测产出模板
    report-template.md        # 报告文件模板
    exec-interaction.md       # 组件库交互姿势手册（跨项目共享）
    exec-example.md           # 执行范例（单用例完整走查）
    exec-log-template.md      # 执行日志模板
    env-template.md           # sdlc/env/ 环境配置模板
  evals/                      # 评估场景（含 TC-01 效率基线）
```

使用方式：

- `/sdlc-test cases <需求名或文档路径>`：生成用例 → 🔒 关卡1，暂停等人审核
- `/sdlc-test static <需求名>`：静态代码检测（三态结论清单）
- `/sdlc-test exec <需求名> [--from TC-xx]`：前端功能测试，支持断点续跑
- `/sdlc-test report <需求名>`：生成报告 → 🔒 关卡2，暂停等人复验

**进度持久化**：阶段进度 checklist + 审核状态写在用例文件头部（非会话内存），跨会话可恢复；`exec` 中断重入时读头部进度决定从哪条用例继续。

**关卡强制**：与 sdlc-intent 相同的措辞暂停等人；且关卡未过（用例头部状态 ≠ 已确认）时，`static`/`exec` 拒绝执行并提示先过关卡——防止跳过人工审核直接跑测试。

触发方式（首期）：人工发起；事件/定时自动触发列为成熟期演进，不进首期。

## 6. 限制与风险清单

1. **判定可靠性**：AI 可能误报（把对的判错）或漏报（把错的判过）。误报靠三方证据交叉验证 + 人工复验压制；**漏报无解**，只能靠用例覆盖度（关卡1 的人工审核正是为此）
2. **探索性/可用性测试不可替代**：视觉审美、交互手感、极端创造性探索仍是人的领域
3. **前端依赖快照可读性**：canvas 重交互、复杂自定义组件可能让 a11y 快照"失明"（降级：截图 + 视觉判断）
4. **执行速度**：LLM 推理循环慢于熟练测试员单步操作；优势在并行与不知疲倦，不在单步速度
5. **用例维护成本**：需求变更需同步改用例（AI 可辅助 diff 提示过期用例）
6. **token 成本**：全流程 agentic 执行成本高于脚本回放；回归量大后评估把高频用例沉降为 Playwright 脚本（M3）
7. **环境依赖**：test 环境可用性、测试数据前置状态是外部前提
8. **写操作影响半径**：AI 会真实执行提交/审核通过类写操作（test 环境影响可控但需注意）；账号文件不入库（gitignore）

## 7. 落地路径（渐进）

| 阶段 | 内容 | 通过标准 |
|---|---|---|
| **M1 试点回测** | 拿已开发完的需求（sdlc/<需求名>/intake/ 三件套现成、代码记忆新鲜）让 AI 全流程跑一遍 | 用已知结果校准 AI 检出率/误报率；产出 ≥1 用例 + ≥1 报告且人工复验可执行 |
| **M2 新需求实测** | 下一个真实提测需求双轨跑（AI + 人工并行一轮，对比后评估单轨） | 双轨结果对比可接受 |
| **M3 回归复用与演进** | 存量用例回归复跑常态化；高频用例沉降 Playwright 脚本；评估定时/事件触发 | 回归成本显著下降 |
