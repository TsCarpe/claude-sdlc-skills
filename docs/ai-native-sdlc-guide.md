## 一、三家共识：为什么流程必须重构

三篇文章立场不同，但核心判断完全一致：

1. **瓶颈转移**：代码生成已被解决。AI 把构建阶段从数周压到数小时，但需求、评审、验证、部署仍以人的速度运行——瓶颈移到了构建阶段的左右两侧 [A][G]
2. **人的注意力移到"门"上**：人不再逐行写/审代码，而是在关键决策点做判断——意图、架构、验收、风险 [A][O][G]
3. **结构化可以规模化，"直觉"不行**：同样的 AI 工具，配上规格文档、测试、防护约束就是智能体工程；裸奔就是直觉式编码。区别不在工具，在配套了多少结构约束、验证手段与人工判断 [G]
4. **AI 放大既有工程文化**：测试完善、架构清晰的团队从 AI 获得巨大增益；工程文化薄弱的团队，AI 同步放大短板 [G]
5. **验证、判断、方向把控，成为新的核心技艺**——取代"写代码"成为工程师的核心价值 [G][O]

## 二、核心思维模型

### 2.1 能力光谱：直觉式编码 → 结构化辅助 → 智能体工程 [G]

| 维度 | 直觉式编码 | 结构化 AI 辅助 | 智能体工程 |
|---|---|---|---|
| 意图描述 | 随意自然语言提示词 | 带示例与约束的详细提示词 | 正式规格文档、架构文档、记忆配置 |
| 验证方式 | "看起来能跑就行" | 人工测试、重点抽查 | 自动化测试套件、CI 门禁、Evals |
| 代码理解 | 几乎不读生成代码 | 选择性审阅关键路径 | 完整审核架构，AI 管实现细节 |
| 错误处理 | 报错丢回给 AI | 人定位根因，AI 修复 | 智能体限定范围内自主排错 |
| 适用场景 | 原型、脚本、个人项目 | 存量库内业务功能 | 生产系统、团队协作 |
| 风险 | 高（一次性代码） | 中 | 低（全流程系统化验证） |

关键判据：**验证机制有两套**——测试（校验确定性逻辑）+ 评估 Evals（校验非确定性的执行轨迹与输出质量）。只有测试没有 Evals，提示词再精妙，本质仍是直觉式编码 [G]。光谱位置取决于业务风险：周末原型可全直觉，支付系统 API 必须智能体工程。

### 2.2 上下文工程：真正的核心技能 [G]

AI 生成代码的质量，不取决于提示词多精巧，而取决于**输入的上下文质量**。核心问题从"如何哄骗 AI 写好代码"变成"**一个新入职成员需要知道什么，如何编码成 AI 可读的格式**"[G]。

六大类上下文：指令、知识、记忆、示例、工具、防护约束 [G]。

核心权衡——静态 vs 动态：
- **静态**（每轮全量加载）：系统指令、规则文件（CLAUDE.md / AGENTS.md）。过多则浪费 token、信号被噪声稀释；过少则智能体遗忘关键规则
- **动态**（按需加载）：任务触发才启用的 Skills、RAG 检索、会话历史。成本低，只在需要时消耗
- 成熟团队把这条边界当**一等架构决策**，像代码一样做版本管理与评审 [G]
- [A] 的对应实践：CLAUDE.md 保持在"新员工第一天所需"以内，错两次的修正就写进去；细则用 Skills / spec 分层按需加载

### 2.3 支撑层公式：智能体 = 模型 + Harness [G]

模型只是发动机（约占体验 10%），支撑层是整车、道路与交通法规（约 90%）。日常用 Claude Code / Cursor 的体验绝大部分来自支撑层而非模型本身。

支撑层六组件 [G]：
1. **指令与规则文件**（CLAUDE.md / AGENTS.md / 子代理提示词）
2. **工具**（函数、MCP 服务、API 及其调用说明）
3. **沙箱与执行环境**（权限与访问边界）
4. **编排逻辑**（子代理生成、模型路由、任务移交）
5. **防护与钩子**（生命周期节点上的确定性代码：改文件后、提交前）
6. **可观测性**（日志、轨迹、token 与延迟统计、行为漂移监控）

实证：不换模型，仅调支撑层，Terminal Bench 2.0 从 30 名外进前五；固定模型只改提示词/工具/中间件，得分 +13.7 [G]。**智能体出错，第一反应不该归咎模型，多数故障是配置问题**：缺工具、规则模糊、防护不足、上下文有噪声 [G]。

### 2.4 工厂模型：开发者产出的是"生产代码的系统" [G]

开发者的核心产出不再是代码，而是一套产出代码的工厂：规格文档与上下文（定义目标）+ 智能体（转实现）+ 测试与门禁（校验正确性）+ 反馈闭环（失败回传修正）+ 防护规则（约束行为）。给智能体定义**成功标准**，而非一步步下指令 [G]。

### 2.5 角色演变：指挥者 vs 编排者 [G]

- **指挥者（Conductor）**：实时结对，细粒度引导，适合复杂调试、陌生代码。风险：人成为吞吐量瓶颈
- **编排者（Orchestrator）**：定义目标、委派智能体、只审产出，适合边界清晰任务。所需新技能：**规格定义、任务拆解、评估能力、系统设计**
- 两者按任务灵活切换，不互斥
- **80% 难题**：AI 快速完成 80%，剩下 20%（边界条件、异常处理、集成逻辑、隐蔽正确性约束）需要深度上下文。AI 的错误不再是语法错，而是"看起来通顺甚至能过简单测试"的逻辑缺陷。应对：AI 擅长的交给 AI，人聚焦模糊需求、架构权衡、正确性校验 [G]

### 2.6 经济学：CapEx / OpEx [G]

- **直觉式编码**：前期投入≈0，但持续运营成本高——昂贵的试错 token 循环、维护税（逆向解读混乱代码）、线上安全修复成本
- **智能体工程**：前期投入高（Schema、测试套件、上下文设计），但边际交付/维护成本大幅下降
- **上下文工程是财务杠杆**：高信噪比上下文提升首次产出成功率，规避昂贵试错循环
- **智能模型路由**：复杂任务用大模型，确定性简单任务（测试生成、CI 监控）路由到小快便宜模型

## 三、六阶段实操

[A] 的主干是**工件链（committed artifact）**：每阶段以提交一个工件结束，下一阶段以读取它开始——intent.md → spec.md → plan.md → diff+测试 → PR+评审记录 → 事故记录。提交链即审计链。人先手动逐步触发，终态是"工件被接受即自动触发下一阶段"的环。以下每阶段融合三家，并附 [O] 的责任框架。

### 3.1 Plan 需求

- **目标**：意图以发起人自己的语言被捕获一次，成为下一阶段可直接消费的版本化工件 [A]
- **实践**：发起人与 AI 头脑风暴产出 `intent.md`（问题/期望结果/受影响系统/约束/开放问题），AI 扮演分析师追问范围与成功标准；发起人修正后提交，产品负责人决定接受与否 [A]。[O]：把智能体接入 issue 系统，读规范→对照代码库→标歧义→拆子任务→估难度；[G]：从产品简报生成用户故事、识别遗漏边界、直接产出交互原型
- **委派**：可行性分析、依赖识别、歧义标注 ｜ **审查**：验证发现准确性、评估估算 ｜ **负责**：优先级与方向由人定 [O]

```markdown
# Intent: claims status self-service
## Problem / Proposed outcome / Affected users & systems / Constraints / Open questions
```

### 3.2 Design 设计

- **目标**：需求与设计压缩进一个会话，政策在写 spec 时就被应用，而非数周后在评审里被发现 [A]
- **实践**：AI 读 `intent.md` 产出 `spec.md`，受组织级 Skills（品牌/安全/合规/UX）约束，标注关切点；产品负责人只审不写；关切点由政策 owner 在工程介入前解决 [A]。[O]：AI 生成样板与脚手架、设计稿转组件、应用设计 token，设计师专注探索替代方案
- **委派**：脚手架、样板、设计转码 ｜ **审查**：是否符合规范/无障碍/集成 ｜ **负责**：设计系统、UX 模式、架构决策 [O]

### 3.3 Build 构建

- **目标**：没有可接受的计划就不动手实现；制度知识变成文件，护栏以代码运行 [A]
- **实践**：
  - **Plan mode 为默认起点**：让 AI 读 `spec.md` 出实施计划（改哪些文件、顺序、证明用的测试），质询计划（会破坏什么/哪步最险/放弃了哪些备选），迭代到"没看过对话的工程师也能照计划实现"，提交为 `plan.md`；实现偏离计划时同 commit 更新 [A]。[O] 的等价物：让智能体提交 PLAN.md 并确认其要跑的命令都能跑通
  - **CLAUDE.md**：新员工第一天所需——命令、约定、架构、AI 常犯的错。错两次的修正写进去；保持一页内；进 git，像代码一样评审 [A]
  - **Skills**：必须一致执行的制度知识写成 Skill（frontmatter 定触发条件）；政策变更改 Skill 即全员生效。Skill 是建议性控制，必须绝对成立的政策要配 Hook 兜底 [A]
  - **Hooks**：构建期确定性护栏——封锁保护路径、编辑后自动格式化、凭证不入 diff [A]
  - **并行**：独立任务各开 worktree 并行会话（2-3 个起步，上限是"一个人能审得过来多少"）；重复作业固化为子代理（.claude/agents/）[A]
- **委派**：规格明确功能的第一版完整实现 ｜ **审查**：设计选择、性能、安全、迁移风险 ｜ **负责**：新抽象、跨模块架构变更、模糊需求 [O]

### 3.4 Test 测试

- **目标**：会话在人看到之前自查自纠；驱动智能体的配置（CLAUDE.md/Skills/Hooks）像代码一样被回归测试 [A]
- **实践**：
  - **反馈回路**：给 AI 单命令可运行的验证手段（make test / 截图对比），完成定义里写明"跑完测试并贴输出"[A]
  - **修 bug 先写失败测试**：让 AI 把 bug 复现为测试，确认按预期失败，提交测试后才允许修——且用 Hook 禁止修 bug 时改测试文件 [A]
  - **持续 Evals**：收集 20-50 个真实任务做评测集，CLAUDE.md/Skills/Hooks 变更或换模型时跑，不达标不许合并；生产事故固化成永久 eval [A]
  - [O]：让测试生成独立于功能实现的会话；审查时警惕占位测试与走捷径
- **委派**：初版测试用例生成 ｜ **审查**：无占位/走捷径、可被智能体运行 ｜ **负责**：测试与规范/体验的对齐 [O]

### 3.5 Deploy 评审与部署

- **目标**：评审双向进行（AI 审 AI 被审），治理在 AI 行动时同步执行；AI 可做到生产门之前的一切，不能越过它 [A]
- **实践**：
  - **AI 进 PR 评审环**：统一评审策略写 `REVIEW.md`（分 pass：bug/安全/对 spec 与 plan 的合规；定义 Important vs Nit；nit 上限；排除生成文件与 CI 已覆盖项）。AI 发现分级列问题，人只判意图与风险；分支保护仍由人批准 [A]
  - **评审反哺 CLAUDE.md**：同类问题被评审标第二次，修正进 CLAUDE.md，从此评审会拦住 [A]
  - **Hooks 作审批门**：生产部署、迁移、受保护路径的修改，用 Hook 强制等待具名审批；block 要自解释（说明原因与审批路径）[A]
  - **CI 集成**：`claude -p` 非交互跑判断类步骤（分诊失败构建、总结 flaky 测试、修 lint、处理 @claude 评论）；写操作全部经分支保护变 PR；回滚路径要预先排练 [A]
- **委派**：第一轮评审 ｜ **审查**：架构一致性、约定、需求符合度 ｜ **负责**：最终合并与生产 [O]

### 3.6 Maintain 维护

- **目标**：环闭合——触发器无人参与地调起 AI，其发现以 `intent.md` 重入管道 [A]
- **实践**：
  - **闭环**：确定性脚本监控指标（如 CI 失败率、部署后 5xx），按 σ 分级响应：1σ 只记录，2σ 只读诊断，3σ 才允许开 PR 或触发预批准 runbook；AI 写诊断为新 `intent.md` 进分流队列 [A]
  - **日志分诊**：经 MCP 开放日志工具，AI 关联日志+git 历史+部署记录定位根因 [O]
  - **定期扫描**：安全扫描从"事件"变"日程"，发现走同样的评审门；大问题写成 intent.md 从 Plan 重入 [A]
  - [G]：遗留系统重构、框架迁移、技术债清理被 AI 大幅解锁——过去"只有原作者懂"的代码现在可安全改
- **委派**：日志解析、异常发现、热修提案 ｜ **审查**：核验诊断、批准补救 ｜ **负责**：新型事件、生产变更、低置信度决策 [O]

## 四、支撑层工具箱速查

| 工具 | 定位 | 强度 | 误区/边界 |
|---|---|---|---|
| CLAUDE.md / AGENTS.md | 新员工手册，静态上下文核心 | 建议 | 塞太满 → 每轮烧 token 还稀释信号；保持一页内 [A][G] |
| Skills | 必须一致执行的制度知识，按需加载的动态上下文 | 建议 | 与 CLAUDE.md 职责混淆；必须绝对成立的政策要 Hook 兜底 [A][G] |
| Hooks | 生命周期节点确定性代码 | 强制 | 构建期 Hook 要快、限定改动文件；审批类 Hook 别放构建期（人回到关键路径上）[A] |
| Evals | 对"驱动智能体的配置"的回归测试 | 门禁 | 只有测试没有 Evals = 仍是直觉式编码 [G] |
| MCP | 把外部系统（部署/日志/issue）变成智能体可调工具 | — | 注意权限范围与沙箱 [A][O] |
| Worktree / 子代理 | 并行会话隔离；重复作业固化 | — | 并行上限 = 一个人审得过来的量 [A] |
| 可观测性 | 轨迹、token、延迟、行为漂移 | — | 没有它无法判断智能体好坏 [G] |

## 五、落地行动清单

### 个人

1. 配 AGENTS.md/CLAUDE.md：先写十行（技术栈/规范/硬规则/流程），**每错一次加一条** [G][A]
2. 生成代码前先写测试与评估——测试是人和 AI 之间的契约 [G]
3. 所有上线输出逐行审：警惕幻觉依赖（不存在的包）、薄弱异常处理、看似精巧的正确性缺陷 [G][O]
4. 选一个重复工作做成第一个智能体原型，完整走一遍构建流程 [G]
5. 持续打磨调试、系统设计、正确性判断能力——AI 放大专业能力，不替代 [G]

### 团队

1. 上下文工程当一等工程实践：规则文件/评估套件/技能库像代码一样 PR 评审、版本管理、有 owner [G]
2. 以评估结果为验收标准，而非 Demo 跑通 [G]
3. 重构针对 AI 代码的评审流程：审查力度 ≥ 人工代码，重点查 AI 典型故障模式 [G]
4. 明确区分原型（直觉式）与生产（智能体工程）的边界：项目/分支/环境级划分 [G]
5. 支撑层是团队共享资产，搭一次反复复用 [G]
6. 渐进式落地：从打标签/去重这类基础工作流起步，再上工单细化、阶段触发 [O]；从手动逐步触发，向"工件接受即触发下一环"演进 [A]

## 六、三家观点对照

| 维度 | [G] Google | [A] Anthropic | [O] OpenAI |
|---|---|---|---|
| 最大的贡献 | 思维模型：光谱/上下文工程/支撑层/工厂模型 | 可抄的作业：六阶段 Plays + 工件链 | 责任框架：每阶段委派/审查/负责 |
| 落地路径 | 按角色分层给建议（个人/管理者/组织） | 按 Play 依赖图推进，先 CLAUDE.md 后闭环 | 渐进式：先基础工作流后高级工作流 |
| 治理观 | 防护约束+评估前置（CapEx） | 治理编码为 hooks/skills，审计链=提交链 | 人最终负责，AI 委派+人核验 |
| 独有内容 | 经济学/模型路由/80% 难题 | Evals in CI、闭环自动化、managed settings | 真实客户案例、文档自动化 |

互补关系：[G] 回答"为什么、往哪去"，[A] 回答"具体怎么做"，[O] 回答"人怎么管、从哪起步"。

## 七、对照本仓库工作流的实践映射

以本方法论的源项目（某 Java DDD 业务系统）+ Claude Code 的现状对照上述框架；流程全貌见 [workflow.md](workflow.md)。

### 已覆盖

### 可补强（候选，按性价比排序）

1. **反馈回路缺失**（Test 阶段最弱项）：项目无测试套件/单命令验证手段，AI 产出主要靠用户人工验。哪怕先建"接口级可运行校验"（启动+curl 冒烟），也是从直觉式向结构化跨一步
2. **确定性 Hook 门禁少**：目前 Hook 主要做上下文注入。可加：禁止改动生成代码/保护路径、提交前规范检查——把"AI 常犯的错"从会话提醒升级为代码强制
3. **CLAUDE.md"错两次即写入"机制未制度化**：MEMORY.md 里沉淀了不少教训（如分页规范、Mapper 被生成器覆盖），可定期把高频教训迁移进 CLAUDE.md/dev_standards 并删减过时项
4. **AI 初轮评审未用**：提交前可让子代理/code review pass 按 checklist 先过一遍，人只处理升级项
5. **Evals 短期不现实但可微缩**：不必上 CI evals，但"同类问题第二次出现就固化成 spec 规则/checklist 项"是可立即执行的微缩版
6. **经济学意识**：简单任务路由小模型、上下文按需加载（CodeGraph 优先于全库 grep）已经在做，可保持自觉

### 一句话总结

当前流程在 **Plan/Design/Build 的工件链与上下文工程**上已相当成熟（任务框架 + plan mode + 分层规范），主要短板集中在 **Test 与 Deploy 的右侧**：反馈回路、确定性门禁、AI 初轮评审。下一步性价比最高的动作是补"验证手段"，而非继续加规范文档。
