# 大需求三段式 Playbook（自顶向下拆分方法论）

> **出处**：本方法论在真实 Java 项目的 Trellis 0.6.x 任务框架定制中打磨成形（2026-09，经真实大需求全链路验证），此处为**框架无关提炼**——任何任务框架、甚至纯目录约定都可复刻。配套产物模板：[templates/large-req-stage1-template.md](../templates/large-req-stage1-template.md)（业务全貌）、[stage2](../templates/large-req-stage2-template.md)（技术骨架）、[stage3](../templates/large-req-stage3-child-prd-template.md)（child prd）。
>
> 术语：**parent** = 需求级容器任务（持有源需求、任务地图、跨 child 验收标准，本身不是实现目标）；**child** = 可独立规划/实现/验证/归档的切片任务。

## 0. 核心思想

**触发条件**（满足任一即强制走三段式）：涉及表结构变更 · 跨业务域 · 功能点 ≥5 · AI 判定为大型且用户确认。

**目的**：把一次大确认拆成多次小确认，每次确认的产物粒度是**人能认真逐行核对的清单**（不是通读长文），防止实现期才暴露规范/业务偏差。三段式是对需求澄清产出物的结构化整理，不替代逐问澄清过程本身。

**三层金字塔**：顶层 parent 做框架（人逐行核对）→ 中层骨架 child 先建公共资产 → 底层业务 child 逐功能点切片（AI 自动执行）。

## 1. 第一段：业务全貌（顶层设计）

**定位**：把已澄清的需求转成一份**业务全貌文档**——人和 AI 不回头读需求原文，即可获得完整自洽的业务心智。功能点清单从业务主线推导，而非全貌从清单拼凑。

**产出顺序**（内部分层，顺序不可倒置）：需求梳理 → 业务逻辑梳理（主流程/状态机/边界）→ **业务主线串联** → 功能点清单（从主线推导）→ 轻确认 → 字段级 ER 表结构（基于已确认的功能点推导，再确认）。

- **业务主线串联**：「角色 × 状态 × 功能点」串联视图（状态为列、角色旅程为行，功能点编号挂在旅程节点上）+ 每角色 2-3 句主线叙事补业务动机。不挂钩时，角色覆盖缺口（某角色本期零交付未显式决策）与横切型功能点（无独立触发角色、覆盖多状态窗口，如系统定时流转）无法在规划期显形，会漏成实现期返工。
- **功能点清单从主线推导**：每个功能点 = 一个可独立验收的交付物，每行携带触发角色 / 状态窗口 / 读写类型（推导的痕迹，不是事后补的列）。
- **ER 必须后置**：ER 从功能点推导，功能点错了 ER 全废；分层确认可锁定返工范围。功能点清单同理后置于业务主线——主线错了清单全废，同一逻辑。
- **角色覆盖结论**：串联视图后附一行/角色（覆盖的功能点数）；零交付角色必须写明原因与去向——「某角色本期不做」是显式决策，不是删功能的副作用。
- **对现有业务的影响（业务级清单）**：复用/扩展哪些既有域与公共组件、影响哪些存量功能、多人协作边界、存量数据风险。技术落点（表/类级）归第二段。
- **承接锚点**：prd 头部记录输入源（sdlc-intent digest 三件套等需求梳理产物、外部基线文档）的文件名与日期版本；口径漂移时以锚点判断是否回溯重审。
- **待确认项（Q 表）机制**：范围内所有未定口径入 Q 表，强制三列——问题 / 当前假设 / **阻塞范围（阻塞哪些功能点）**。硬阻塞规则：阻塞写接口核心逻辑的 Q 未决 → 对应功能点的开发任务不得启动；不影响其他功能点正常推进。**未决口径只锁对应功能点，不阻塞全局**——人不在场时其余切片照常推进。禁止无阻塞范围标注的挂起项进入第三段。
- **体检问题去向表**：存在需求体检产物（sdlc-intent audit）时必填——全部 🔴/🟡 问题须有去向：已承接（落点=功能.Fxx）/ 转 Q 表 / 本期不做+理由。无去向即确认点①不通过。

**确认点①**：人按「串联视图逐角色逐段 + 功能点 ↔ 需求原句对照表 + 影响清单 + Q 表阻塞范围列 + 体检问题去向表」逐行核对，不做通读式阅读理解。

## 2. 第二段：技术骨架

**定位**：承上启下——把第一段业务全貌翻译成技术骨架，给第三段 child prd 提供**不用现场设计**的技术依据。判据：child prd 应只做「内联 + 裁剪」；若 child prd 一半内容是现场设计，说明第二段产物缺项。

**产物一：接口契约（分级粒度）**——功能点 → 接口映射表，每行挂功能点编号与消费的业务规则/主线节点。

- 写接口（save/edit 等复杂入参）：**字段级**——字段名 / 嵌套结构 / 口径来源（消费哪条业务规则或 ER 字段）/ 校验归属（声明式校验还是应用层校验器）；不含校验注解细节。
- 读接口：**出参字段清单 + 口径来源**（统计/推导口径与 D 表决策挂钩），展示细节（label/格式拼接）留 child。

**产物二：公共资产清单（六类，每项标注被哪些 child 消费、归属哪个 child 交付）**：

1. 枚举与码表（code/label 与 ER 及实体注释对齐；**跨域公共枚举扩展值须声明影响面**）
2. 常量与 key 空间（锁 key、定时任务 taskId、错误消息文案模板——统一收口，禁止 child 内散落定义）
3. 命名空间约定（URL 前缀 / 包路径 / 类名前缀 / 校验 profile 前缀 / 多人协作方法名避让）
4. 公共 DTO 子结构骨架（文件信息体、列表行公共字段、快照结构——多 child 同构结构只定一版）
5. 共享存量资产扩展影响声明（改公共 Req/组件须列受影响 profile/域）
6. DDL 与索引脚本归属

边界：不重复项目通用规范约定，只收本需求域新增/扩展项。

**产物三：公共组件清单**——复用/新建分列；每项必须标注：依据哪些功能点的哪些需求（防过度抽象）、须遵循的规范文档路径。

**产物四：关键实现决策表（D 表）——必答八类别**：并发控制 / 子表对账与软删策略 / 状态联动（定时任务、生命周期钩子）/ 统计口径 / 权限与数据范围 / 回显与回传闭环策略 / 全链路时间等格式 / 外部依赖降级。每类别必须有显式决策（「不适用」也要写明），**漏答不得过确认点②**；类别可随需求域扩展，扩展项在 D 表顶部列明。

**产物五：child 实现顺序与依赖表**——必须含共享物归属列：跨 child 共享物（公共类/枚举/常量/工具/DDL）由哪个 child 创建、哪些 child 复用；他人已建/在途组件锚点。横切功能点在此标注「随宿主 child 交付 + 核验矩阵」。

**组件清单是脚手架不是合同**：第三段发现组件接口不合理时，调整组件不算偏差、不需回写第二段文档。**豁免仅限组件接口**——D 表决策、接口契约、公共资产的偏差仍按回写规则处理。

**确认点②**：核对对象 =「接口契约表（分级粒度）」+「组件双对照表（组件 ↔ 规范条目、组件 ↔ 功能点）」+「D 表必答类别逐项齐套」+「公共资产清单（六类齐套 + 归属明确）」+「实现顺序表共享物归属列」，人逐行核对。

## 3. 第三段：逐功能点实现

- **骨架 child 先行**：公共资产清单非空时，必须先建骨架 child（交付枚举/常量/DDL/包目录/公共子结构）并完成后，业务 child 方可启动；后续 child 只消费公共资产、不得新建同功能项（确需新增须回写公共资产清单）。防多切片重复建设与命名漂移。
- **横切功能点不单独建 child**：按第一段主线串联的「触发角色 / 状态窗口」识别横切功能点（无独立触发角色、代码落点分散在多个接口，如定时状态流转）——标注「随宿主 child 交付 + 核验矩阵」（矩阵列：预期联动 / 落点宿主 child / 核验结论），宿主 child 完成后逐行核验补记。
- **child prd 内联瘦身**：只内联**本功能点特有的裁剪/组合结论**（本接口特有的校验组合、边界、口径选择）；通用上游结论（接口契约、公共资产、关键业务规则、ER 字段）不复制进 prd，由任务上下文清单登记上游文件注入（框架支持自动注入则用之；否则在 prd 头部列上游文件清单，执行前先读）——**注入替代复制，防内联副本漂移**。禁止裸链接引用：通用结论必须登记注入、特有结论必须内联，两者都缺 = 执行 agent 会瞎补。
- 另附技术级验收标准。

**确认点③**：child prd 评审通过后才能启动开发。核对对象 =「与 design 接口契约的符合度（无现场设计痕迹；若有，回第二段补契约）」+「内联/注入完整性（通用结论已注入、特有结论已内联）」+「技术级 AC 可测性」。

## 4. 偏差分级回写规则（实现中发现设计缺陷时）

- **局部偏差**（不影响其他功能点）：在 child 内记录后直接改，不回写。
- **影响 ER / 接口契约 / 公共组件 / 公共资产的偏差**：回写 parent design 文档，仅重审受影响的 child，不全量重审。
- 组件接口调整不算偏差（见第二段「脚手架不是合同」）。

## 5. 编码前置约束（第二/三段通用）

组件代码与业务代码编写前，必须先读组件清单 / child prd 中标注的规范文档。规范注入是硬性步骤——防止执行 agent 因上下文丢失规范信息而按存量代码或通用常识写码。

## 6. 混合工作模式（何时不用三段式）

三段式只对大需求强制。日常任务按规模路由：**轻量任务/逐接口切片** → 主会话直接执行（先出「入参/出参/逻辑」方案，人确认再写码）；**复杂任务/大需求 child** → 分发独立子代理执行。轻量判定参考：影响 ≤2 层且 ≤3 文件。杀鸡不用牛刀，但牛刀的架子（确认点思维、规范前置）随时可借。
