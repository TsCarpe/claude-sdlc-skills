# SDLC 流程串联与 ID 体系统一方案（P1+P2）

> 日期：2026-09-10 ｜ 状态：**已实施**（P1+P2 已落地为本仓库 skills 现行机制——digest 的 FR 编号列与 ID 声明行、跨产物命名空间引用、review issues 的落点/状态列、放行前闭环校验均已生效；本文作为设计决策记录收录，文末附落地核对）
> 范围：sdlc-intent / 大需求三段式（源项目任务框架 trellis，属项目侧）/ sdlc-gate / sdlc-test 四环节的标识符体系与交界衔接机制。
> 决策背景：实测调研（一个真实需求的全链路产物 + 四 skill 定义文件）发现两类根因问题，用户选定 P1（规范层）+P2（机制层）改进，P3（编号前缀重排）观望（后经一个真实需求验证后关闭，见 §6）。

### 1.2 根因一：ID 命名空间无全局规划（撞名实测）

| 前缀 | 含义 A | 含义 B | 含义 C |
|---|---|---|---|
| D | design.md 实现决策 D1~D11 | review 分歧 D-01~D-12 | digest §9 demo 增量小节 D1~D3（另有误报模式沉淀 D1-D7） |
| A | digest 假设 A1~A30 | review 架构 A-01~A-11 | — |
| T | ER 决议 T1（报名时间窗口） | audit 主题 T1（专家分配） | review 可测性 T-01~ |
| S | ER 决议 S2 | review 数据 S-01~ | — |
| R | sdlc-test 轮次 R1/R2 | sdlc-test 追踪表规则编号 R1 | ER 决议 R1 |
| P | audit 问题 P01~ | 用例优先级 P0/P1/P2 | — |

同一前缀最多 4 套含义，全靠文件语境区分，无登记表、无消歧规则。

## 2. P1 规范层设计

### 2.1 全局 ID 命名空间注册表（核心）

**规则：跨产物引用一律写 `命名空间.编号`；产物内部自引用可裸编号。** 命名空间注册如下（固定，新增产物须先注册命名空间）：

| 命名空间 | 指向产物 | 编号格式 | 含义 |
|---|---|---|---|
| `需求.FR-xx` | digest §7 规则表（**新增编号列**） | FR-01 起连续 | 需求规则/口径条目 |
| `需求.A-xx` | digest §8 假设清单 | A1 起（保留现状） | 梳理假设 |
| `体检.P-xx` | audit 问题明细 | P01 起（保留现状） | 体检问题 |
| `PM.#n` | pm-checklist | #1 起（保留现状） | 问 PM 条目 |
| `功能.F-xx` | prd 功能点清单 | F01 起（保留现状） | 功能点 |
| `确认.Q-xx` | prd Q 表 | Q1 起（保留现状） | 待确认项 |
| `设计.D-xx` | design.md D 表 | D1 起（保留现状） | 实现决策 |
| `ER.X` | ER/状态 puml 决议 | E/U/S/R/O/T + 数字 | 表结构与状态决议 |
| `评审.D-/A-/S-/T-xx` | review issues | 现状四前缀 | 分歧/架构/数据/可测性 issue |
| `用例.TC-xx` | cases 用例明细 | TC-01 起（保留现状） | 测试用例 |
| `缺陷.BUG-xx` | cases 缺陷跟踪 | BUG-01 起（保留现状） | 缺陷 |
| `静态.0x` | static.md 疑似偏差 | 静态-01 起（保留现状） | 静态检测偏差 |

设计要点：

- **不重排任何现有前缀**（P3 观望）——撞名由命名空间前缀消歧：`设计.D6` vs `评审.D-02` vs digest 内部小节 D2（digest §9 的 demo 小节编号属文档内部结构，不进注册表，禁止跨产物引用它；确需引用时引章节号）。
- **R 撞名顺带消解**：追踪表规则编号 `R1`（cases.md:35 / static-check-template.md:16）随 FR 引入**作废**——追踪表行主键改用 `需求.FR-xx`，轮次 R<N> 成为 R 前缀唯一含义。
- pm-checklist 内的「关联 Pxx」维持裸编号（同属 req 产物族，且 PM 可读性优先）；对产物族之外引用 audit 条目时才写 `体检.P04`。
- **内联释义规则保留并升级**：跨产物引用首次出现仍须带中文短描述（沿用 design-techniques.md 硬规则），格式如「资源驳回后流转（体检.P04）」。

### 2.2 产物头部 ID 体系声明

每个产物文件头部（现有元数据区）追加一行声明，例：

```markdown
> ID 体系：本文件产出 需求.FR-xx（§7 规则）、需求.A-xx（§8 假设）；外部引用本文条目须带命名空间
```

目的：读者打开任一产物即知本文件产出/可被引用的编号，消除「D-02 是什么的 D」类困惑。各产物声明内容见 §4 改动清单。

### 2.3 digest 规则表行级 ID（FR）

- digest §7「关键规则与口径表」加「编号」列，FR-01 起连续、新增不重排（与 TC 编号同纪律，保证下游引用稳定）。
- 收益链：sdlc-test 双向追踪表行主键 = `需求.FR-xx`（替代自造 R1 与自由文本来源）；static 阶段「从梳理文档关键规则逐条提取」改为按 FR 逐条提取；sdlc-gate 交叉审查「字段级断言/边界值口径」维度可按 FR 对齐。
- 状态机迁移边、功能点矩阵仍是追踪表合法来源（design-techniques.md 优先级不变），引用格式写章节（如 §6 状态机 S2→S3 边）；不为它们新造编号，控制改动面。

## 3. P2 机制层设计

### 3.1 体检问题去向表（承接闭环）

**问题**：audit 的 P 编号与 Q 表无映射要求，未答复问题是否有承接全靠人记（断链实例：P04/P15 无去向记录）。

**机制**：大需求确认点① 新增核对件「体检问题去向表」，落在 parent prd.md：

```markdown
## 体检问题去向（存在 audit 时必填；🔴/🟡 全部须有行，🔵 可省）

| 体检编号 | 级 | 去向 | 落点 | 说明 |
|---|---|---|---|---|
| 体检.P04 | 🔴 | 已承接 | 功能.F07 | PM 答复：公示开始后才能执行颁奖 |
| 体检.P11 | 🔴 | 转 Q 表 | 确认.Q6 | 学科来源待定 |
| 体检.P15 | 🟡 | 本期不做 | — | 理由：修改专家窗口归下期 |
```

- 去向三选一：**已承接**（落点=功能.Fxx）/ **转 Q 表**（落点=确认.Qxx，走 Q 表硬阻塞规则）/ **本期不做**（必填理由）。
- 与 audit 状态列的关系：去向表是**设计侧承接决策**的记录，不替代 audit 状态列；audit 状态仍由 PM 回复/用户拍板回写（修复断链 2 需在 sdlc-intent 回写纪律中补一句：回写 audit 状态时同步刷新执行摘要计数——见 §4 第 3 项）。
- **轻量需求兜底**（不走三段式）：挂在 sdlc-gate 前置输入——技术设计文档（`sdlc/<需求名>/design.md`）头部须含同款「体检问题去向」小节（存在 audit 时）；完全跳过 sdlc-gate 的逐接口轻量切片不强制（改动面控制在有评审环节的链路）。

### 3.2 裁决执行状态列（修订闭环）

**问题**：review 裁决=落改后，修订靠人手工执行，无落点与状态字段（断链实例：S-04 漏执行）。

**机制**：issues 文件明细表（分歧清单 + 三个角色表）与裁决记录汇总表，在「裁决｜理由」列后新增 **「落点/状态」** 列：

- 取值口径：`落点：<文件+位置，命名空间引用> ｜ 待执行` → 执行后改 `已执行`；裁决=驳回/存疑/权衡记档的条目填 `—`。
- **Step 4 落改动作必填落点**：裁决「落改（摘要）」时必须同时给出落点（如 `cases TC-69` / `design §4 接口契约`），禁止只写改动摘要。
- **Step 5 放行前闭环校验（新增硬规则）**：置「已放行」前逐条核对——裁决=落改的每条，落点非空且状态=已执行；不满足则拦截并逐条列出未执行项。直接防 S-04 类批量组吞条目/漏执行。

## 5. 存量兼容

- 已产出的存量需求产物**不回改**，新语法自下一个需求起生效。
- 旧式裸编号引用容错：下游读到裸编号时按文件语境消歧并在产出中补全为命名空间格式（提示不阻断）。
- FR 编号是新增列，不影响 digest 既有结构；TC/BUG/P/A/D 编号格式全部保留，仅引用方式变化。

## 6. 验证方式与结果

下一个真实需求全链路走一遍，观察三点：

1. **引用可机读回查**：cases 追踪表 / review issues 中的每条外部引用，能否按 `命名空间.编号` 一跳定位到目标条目（对照 D6 漂移类问题是否被消解）；
2. **确认点①映射表自然产出**：第一段是否在存在 audit 时生成去向表，🔴/🟡 无漏行；
3. **放行闭环校验生效**：sdlc-gate Step 5 是否能拦住「裁决=落改但未执行」的条目。

三点均自然发生且无显著增加交互负担 → P3（编号前缀重排）确认无必要，已关闭。
